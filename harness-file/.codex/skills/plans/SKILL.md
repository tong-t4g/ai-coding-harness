# 编写计划

## 概述

编写详尽、完备的实施计划。编写时需假设负责编码的工程师**完全不了解我们的代码库，且编码品味不可控**。为此，必须事无巨细地记录他们所需的一切上下文：每项任务需要动用哪些文件、具体的代码实现、需要对齐的测试用例、必须查阅的文档以及自动化验证方法。将整体计划拆解为“原子级”的任务。严格遵循 DRY（别重复自己）、YAGNI（你不会需要它）、TDD（测试驱动开发）和高频提交原则。

假设该工程师是一名资深开发者，但对我们的工具链或业务领域几乎一无所知，且对优秀的测试设计缺乏经验。

**开始时声明：** “我正在调用 plans skill 来制定实施计划。”

**计划文件保存路径：** `openspec/plans/YYYY-MM-DD-<feature-name>.md`
- （若用户指定了计划存储路径，则优先覆盖此默认路径）

## 范围检查

若 Spec 涵盖了多个相互独立的子系统，在头脑风暴阶段就应该将其拆分为独立的子项目 Spec。如果此前未做拆分，请在此处建议将其拆解为多份独立的计划 —— 每个子系统对应一份。每份计划都必须能够独立交付出可运行、可测试的软件。

## 文件结构

在定义具体任务之前，必须先梳理出将要创建或修改哪些文件，并明确划分各自的职责。这是锁定架构解耦决策的关键环节。

- **高内聚，低耦合**：设计的单元必须具备清晰的边界和定义明确的接口。每个文件应当仅承担一项核心职责（单一职责原则）。
- **上下文聚焦**：当代码体量能够被完整塞进上下文窗口时，你的推理准确度最高，且当文件聚焦时，你的代码编辑也更可靠。相比于承担过多职责的庞大文件，应更倾向于小巧、聚焦的代码文件。
- **空间局部性**：协同变更的文件应当存放在邻近的目录。应按职责进行垂直拆分，而非按技术分层（如 MVC）进行水平拆分。
- **尊重既有模式**：在现有代码库中，遵循已有的设计范式。若代码库惯用大文件，切勿单方面进行重构 —— 但如果你要修改的文件已经臃肿不堪，在计划中加入“文件拆分”任务则是合理的。

这一结构将直接作为任务拆解的输入。每项任务所产出的变更都必须是自包含的，且在逻辑上能独立成立。

## 任务粒度合理

任务是承载独立“测试-运行”闭环、且值得触发一次独立代码评审关卡的**最小工作单元**。在划分任务边界时：将初始化设置、配置、脚手架搭设和文档编写等步骤，直接归并到需要这些交付物的具体任务中；**仅在评审人员能够做到“有理由驳回 A 任务、同时批准相邻的 B 任务”的逻辑切分点上进行任务拆分**。每项任务的终点，都必须是一个可独立测试的交付物。

## 原子级任务粒度

**每个步骤仅包含一个单一动作（耗时约 2-5 分钟）：**
- “编写一个必定失败的测试用例”
- “运行该测试，确认为失败状态”
- “编写达成测试通过的最小化代码”
- "运行测试，确保全量通过"
- “Commit 代码”

## 计划文档头部规范

**每份计划文档必须【强制】以下列头部格式开头：**

```markdown
# [特性名称] 实施计划

**核心目标：** [用一句话描述本计划将构建什么特性]

**架构设计：** [用 2-3 句话阐述技术实现路线/方案]

**技术栈：** [核心技术/依赖库]

## 全局约束

[此处罗列 Spec 中项目级的硬性要求 —— 例如版本底线、依赖库限制、命名与文案规范、平台级要求等。每行一条，必须从 Spec 中一字不差地原样复制。每项任务的合规要求默认隐式包含本节内容。]

---
```

## 任务结构模板

````markdown
### 任务 N：[组件名称]

**关联文件：**
- 新建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 测试：`tests/exact/path/to/test.py`

**接口定义：**
- 输入依赖：[本任务需要依赖哪些前置任务的产出 —— 必须写明精确的函数/方法签名]
- 输出提供：[后续任务所依赖的信息 —— 必须写明精确的函数名、参数及返回值类型。任务的执行者只能看到当前任务；此模块是他们了解相邻任务命名与类型的唯一渠道。]

- [ ] **步骤 1：编写一个必定失败的测试用例**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **步骤 2：运行测试以验证其确实失败**

命令：`pytest tests/path/test.py::test_name -v`
预期结果：失败 (FAIL)，报 "function not defined" 错误

- [ ] **步骤 3：编写最小化实现代码**

```python
def function(input):
    return expected
```

- [ ] **步骤 4：运行测试以验证其顺利通过**

命令：`pytest tests/path/test.py::test_name -v`
预期结果：通过 (PASS)

- [ ] **步骤 5：提交代码**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## 严禁使用占位符

每一个步骤都必须包含工程师开箱即用的真实内容。以下情况皆被定义为**“计划缺陷”**，严禁出现：
- 出现 "TBD"、"TODO"、"稍后实现"、"补充细节" 等字样。
- 模糊表述如 “添加适当的异常处理” / “添加校验” / “处理边界情况”。
- 仅写 “为上述代码编写测试”（但未给出具体的测试代码块）。
- 使用 “类似于任务 N” 的表述（必须复制并重写代码 —— 工程师可能会打乱顺序交叉阅读任务）。
- 仅描述操作步骤而不展现实现细节（代码相关步骤必须附带具体代码块）。
- 引用了从未在任何任务中定义过的类型、函数或方法。

## 自检

完成整份计划的编写后，请带着空杯心态重新审视初始的 Spec，并对照 Spec 对计划进行走查。**这是你需要自主运行的核对清单，而非派发给子智能的任务。**

**1. 需求覆盖率**：快速浏览 Spec 的每个章节/需求。你是否能精确指出是哪一项任务实现了它？列出所有的遗漏。
**2. 占位符扫描**：在计划中全面检索上述“严禁使用占位符”章节中提及的红线模式。发现即修复。
**3. 类型一致性**：你在后续任务中使用的类型、方法签名和属性名称，是否与你在前置任务中定义的完全吻合？例如在任务 3 中叫 `clearLayers()` 的函数，在任务 7 中被写成了 `clearFullLayers()`，这就是一个 Bug。

一旦发现问题，直接修复。无需重新启动评审流水线 —— 修正后继续前进即可。如果发现某个 Spec 需求漏掉了，直接补齐对应任务。

## 执行交接

保存计划文件后，向用户提供执行模式的自由选择：

**“计划已构建完毕，并成功保存至 `openspec/plans/<filename>.md`。现有以下两种执行方案可供选择：**

**1. 子智能体驱动模式 (推荐)** —— 我将针对每个任务分别派发一个干净的子智能体去执行，并在任务切换间隙进行人工评审。该模式迭代速度极快。

**2. 行内会话执行模式** —— 在当前会话中直接调用 `executing-plans` 技能，通过设置评审检查点进行批量化任务执行。

**请问您倾向于采用哪种方案？”**

**若用户选择“子智能体驱动模式”：**
- **【强制调用子技能】**：调用 `superpowers:subagent-driven-development`。
- 采用 “单任务派发干净子智能体 + 双阶段评审” 的流水线。

**若用户选择“行内会话执行模式”：**
- **【强制调用子技能】**：调用 `superpowers:executing-plans`。
- 采用 “带有人工介入检查点的批量化执行” 流水线。
