# 编写计划

## 概述

编写完整的开发/实现计划。假设负责编码的工程师**完全不了解代码库，且工程判断未必可靠**。记录他们所需的全部上下文：每项任务要修改哪些文件、实现代码、测试、可能需要查阅的文档，以及如何验证。将整体计划拆解为小而明确的任务。严格遵循 DRY（别重复自己）、YAGNI（你不会需要它）、TDD（测试驱动开发）和高频提交原则。

假设该工程师是一名资深开发者，但对我们的工具链或业务领域几乎一无所知，且对优秀的测试设计缺乏经验。

**开始时声明：** “我正在使用 plans 技能制定实现计划。”

**上下文：** 是否使用完整模式以及如何隔离 worktree，由执行阶段决定。执行阶段会把存在依赖或文件重叠的任务聚合为执行单元，每个执行单元使用一个 git worktree。

**计划文件保存路径：** `openspec/plans/YYYY-MM-DD-<feature-name>.md`
- （若用户指定了计划存储路径，则优先覆盖此默认路径）

## 范围检查

若规格说明（Spec）涵盖多个相互独立的子系统，应该在需求确认阶段就已将其拆分为独立的子项目规格说明。如果此前未做拆分，请建议将其拆解为多份独立的计划，每个子系统对应一份。每份计划都必须能够独立交付可运行、可测试的软件。

## 文件结构

在定义具体任务之前，必须先梳理出将要创建或修改哪些文件，并明确划分各自的职责。这是锁定架构解耦决策的关键环节。

- 设计边界清晰、接口明确的单元。每个文件只承担一项明确职责。
- 当代码和文件保持聚焦时，推理与编辑更可靠。优先选择小而聚焦的文件，避免单个文件承担过多职责。
- 会协同变更的文件应放在一起。按职责拆分，而非按技术层拆分。
- 在现有代码库中遵循既有模式。若代码库惯用大文件，不要单方面重构；但若待修改文件已难以维护，在计划中加入拆分任务是合理的。

这一结构将直接作为任务拆解的输入。每项任务必须形成可审查的逻辑闭环，但可以显式依赖前置任务；不要为了提高并行率而扭曲任务边界。存在依赖或需要修改同一文件的任务会在执行阶段进入同一执行单元。

## 任务粒度合理

任务是承载“测试-运行”闭环、且值得单独判断完成与否的**最小工作单元**。在划分任务边界时：将初始化设置、配置、脚手架搭设和文档编写等步骤，直接归并到需要这些交付物的具体任务中；**仅在评审人员能够做到“有理由驳回 A 任务、同时批准相邻的 B 任务”的逻辑切分点上进行任务拆分**。每项任务的终点都必须在其已声明的前置任务完成后可测试。不要为“每个任务一个子智能体”而拆分任务；子智能体边界由执行阶段的执行单元决定。

## 小步任务粒度

**每个步骤仅包含一个单一动作（耗时约 2-5 分钟）：**
- “编写预期失败的测试”
- “运行该测试，确认为失败状态”
- “编写让测试通过的最小实现”
- “运行测试，确认通过”
- “提交代码”

## 计划文档头部规范

**每份计划文档必须以下列头部格式开头：**

```markdown
# [特性名称] 实现计划

> **面向执行智能体：** **必需执行方式：** 使用 `subagent-implement`（推荐；由其聚合执行单元），或在当前会话中按任务逐项执行本计划。使用复选框（`- [ ]`）跟踪步骤进度。

**核心目标：** [用一句话描述本计划将构建什么特性]

**架构设计：** [用 2-3 句话阐述技术实现路线/方案]

**技术栈：** [核心技术/依赖库]

## 全局约束

[此处罗列规格说明中项目级的硬性要求，例如版本底线、依赖库限制、命名与文案规范、平台级要求等。每行一条，必须从规格说明中原样复制精确值。每项任务的合规要求默认隐式包含本节内容。]

---
```

## 任务结构模板

````markdown
### 任务 N：[组件名称]

**关联文件：**
- 新建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 测试：`tests/exact/path/to/test.py`

**执行关系：**
- 前置任务：无 / `任务 1`、`任务 2`（必须列全；只写直接依赖）

**接口定义：**
- 输入依赖：[逐项写明前置任务编号及其产出，必须包含精确的函数/方法签名；没有则写“无”]
- 输出提供：[后续任务所依赖的信息 —— 必须写明精确的函数名、参数及返回值类型。任务的执行者只能看到当前任务；此模块是他们了解相邻任务命名与类型的唯一渠道。]

- [ ] **步骤 1：编写预期失败的测试**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **步骤 2：运行测试以验证其确实失败**

命令：`pytest tests/path/test.py::test_name -v`
预期结果：失败 (FAIL)，报 "function not defined" 错误

- [ ] **步骤 3：编写最小化实现代码**

```python
def function(input):
    return expected
```

- [ ] **步骤 4：运行测试以验证其顺利通过**

命令：`pytest tests/path/test.py::test_name -v`
预期结果：通过 (PASS)

- [ ] **步骤 5：提交代码**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## 严禁使用占位符

每一个步骤都必须包含工程师开箱即用的真实内容。以下情况皆被定义为**“计划缺陷”**，严禁出现：
- 出现 "TBD"、"TODO"、"稍后实现"、"补充细节" 等字样。
- 模糊表述如 “添加适当的异常处理” / “添加校验” / “处理边界情况”。
- 仅写 “为上述代码编写测试”（但未给出具体的测试代码块）。
- 使用 “类似于任务 N” 的表述（必须复制并重写代码 —— 工程师可能会打乱顺序交叉阅读任务）。
- 仅描述操作步骤而不展现实现细节（代码相关步骤必须附带具体代码块）。
- 引用了从未在任何任务中定义过的类型、函数或方法。

## 自检

完成整份计划后，以全新的视角重新审视初始规格说明，并对照规格说明走查计划。**这是你需要自主运行的核对清单，而非派发给子智能体的任务。**

**1. 规格覆盖率**：快速浏览规格说明的每个章节/需求。你是否能精确指出是哪一项任务实现了它？列出所有遗漏。
**2. 占位符扫描**：在计划中全面检索上述“严禁使用占位符”章节中提及的红线模式。发现即修复。
**3. 类型一致性**：你在后续任务中使用的类型、方法签名和属性名称，是否与你在前置任务中定义的完全吻合？例如在任务 3 中叫 `clearLayers()` 的函数，在任务 7 中被写成了 `clearFullLayers()`，这就是一个 Bug。
**4. 执行关系完整性**：每项任务是否列全直接前置任务？`输入依赖` 是否与 `前置任务` 一致？是否存在依赖环？若存在，说明任务边界有缺陷，必须修正。
**5. 文件所有权完整性**：每项任务的 `关联文件` 是否覆盖全部新建、修改和测试文件？同一路径出现在多个任务中是允许的，但必须如实列出，执行阶段会据此聚合执行单元。

`关联文件` 必须使用 Git 中大小写一致的精确仓库相对路径，只允许可选的末尾行号范围；不得使用目录、glob 或自然语言代替文件路径。

一旦发现问题，直接修复。无需重新启动评审流程，修正后继续即可。如果发现某项规格说明需求遗漏，直接补齐对应任务。
