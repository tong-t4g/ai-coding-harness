审查用户指定的固定基准点与当前 `HEAD` 之间的差异：

- **规范轴（Standards）**：代码是否符合仓库中已记录的编码规范？
- **需求轴（Spec）**：代码是否忠实实现了来源 Issue、PRD 或规格？

并行运行两个子智能体，隔离两轴的上下文，再汇总各自的发现。

任务追踪器应已提供。若缺少 `docs/agents/issue-tracker.md`，运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 固定基准点

将用户提供的值作为基准点，例如提交 SHA、分支名、标签、`main` 或 `HEAD~5`。用户未指定时，询问基准点。

记录一次差异命令：`git diff <fixed-point>...HEAD`。三点语法表示相对共同祖先进行比较。同时使用 `git log <fixed-point>..HEAD --oneline` 获取提交列表。

继续前先运行 `git rev-parse <fixed-point>`，确认基准点有效，并确认差异非空。引用无效或差异为空时，由主智能体停止流程，不要交给子智能体处理。

### 2. 确定需求来源

按以下顺序查找原始需求：

1. 从提交信息中查找 Issue 引用，例如 `#123`、`Closes #45` 或 GitLab `!67`，再按 `docs/agents/issue-tracker.md` 中的流程获取详情。
2. 检查用户通过参数提供的文件路径。
3. 在 `docs/`、`specs/` 或 `.scratch/` 中查找与分支名或功能匹配的 PRD 或规格文件。
4. 若仍未找到，询问用户规格所在位置。若用户确认没有规格，跳过需求轴子智能体，并报告“无可用需求规格”。

### 3. 确定规范来源

查找仓库中所有说明代码应如何编写的文档，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除仓库规范外，规范轴始终使用下面这组固定的 Fowler 代码异味（《重构》第三章）作为基准。即使仓库没有规范文档，这组基准也适用，但受两条规则约束：

- **仓库规范优先**：仓库中明确记录的规范始终优先；若仓库规范认可某种被基准标为异味的写法，则不报告该异味。
- **异味属于工程判断**：每种异味都是带名称的启发式判断，例如“可能存在依恋情结”，不能视为硬性违规。跳过已由工具自动检查的规则。

按照“异味是什么 → 如何改进”将以下基准逐项与差异对照：

- **神秘命名（Mysterious Name）**：函数、变量或类型的名称没有说明其职责或保存的内容。→ 重命名；如果找不到准确的名称，说明设计本身含糊。
- **重复代码（Duplicated Code）**：同一种逻辑结构出现在变更的多个代码块或文件中。→ 提取共有逻辑，并让各处复用。
- **依恋情结（Feature Envy）**：方法访问另一个对象的数据多于自身对象的数据。→ 将方法移到它所依赖的数据所在对象。
- **数据泥团（Data Clumps）**：同一组字段或参数总是一起出现，暗示它们应成为一个类型。→ 将它们封装为一个类型并传递该类型。
- **基本类型偏执（Primitive Obsession）**：使用基本类型或字符串表示值得拥有独立类型的领域概念。→ 为该概念建立小型专用类型。
- **重复的 switch（Repeated Switches）**：针对同一类型的 `switch` 或 `if` 级联在变更中重复出现。→ 使用多态替代，或让各处共用同一映射表。
- **霰弹式修改（Shotgun Surgery）**：一个逻辑变更迫使差异中多个文件发生分散修改。→ 将共同变化的内容收拢到同一模块。
- **发散式变化（Divergent Change）**：同一文件或模块因多个互不相关的原因而修改。→ 拆分模块，使每个模块只因一个原因发生变化。
- **夸夸其谈通用性（Speculative Generality）**：为规格未要求的需求增加抽象、参数或扩展点。→ 删除这些设计并内联，直到出现真实需求。
- **过长消息链（Message Chains）**：调用方依赖 `a.b().c().d()` 一类过长的导航链。→ 在第一个对象上用一个方法隐藏后续导航。
- **中间人（Middle Man）**：类或函数的大部分工作只是向下转发调用。→ 移除中间层，直接调用真正的目标。
- **被拒绝的馈赠（Refused Bequest）**：子类或实现类忽略或覆写了所继承的大部分行为。→ 放弃继承，改用组合。

### 4. 并行运行两个子智能体

在同一条消息中发起两个 `Agent` 工具调用，二者均使用 `general-purpose` 子智能体。

**规范轴子智能体提示词**应包含：

- 完整的差异命令和提交列表。
- 第 3 步找到的规范文件，以及完整粘贴的代码异味基准；子智能体无法通过其他途径获得该基准。
- 任务说明：“按文件或代码块报告：(a) 差异中每一处违反已记录规范的问题，并引用规范文件和具体规则；(b) 发现的基准异味，并注明异味名称及引用对应代码。区分硬性违规和工程判断：违反仓库规范可以是硬性问题，基准异味只能是工程判断，且仓库规范优先于基准。跳过工具已经检查的规则。篇幅不超过英文 400 词或约 800 个汉字。”

**需求轴子智能体提示词**应包含：

- 完整的差异命令和提交列表。
- 需求规格的路径或已获取的内容。
- 任务说明：“报告：(a) 规格要求但缺失或只实现了一部分的内容；(b) 差异中规格未要求的行为，即范围蔓延；(c) 表面已经实现、但实现逻辑可能错误的需求。每项发现都必须引用规格原文。篇幅不超过英文 400 词或约 800 个汉字。”

若没有需求规格，跳过需求轴子智能体，并在最终报告中注明。

### 5. 汇总

分别在 `## Standards` 和 `## Spec` 标题下原样呈现报告，或只做轻微整理。两轴有意保持独立，不要合并发现，也不要跨轴重新排序。

最后用一行总结每个轴的发现数量；若该轴存在问题，再指出该轴最严重的一项。不要从两个轴中选出一个“全局最严重问题”。

## 为什么使用双轴

一次变更可能通过其中一轴，却未通过另一轴：

- 代码遵守全部规范，却实现了错误的功能 → **规范轴通过，需求轴失败。**
- 代码完全实现 Issue 要求，却违反仓库约定 → **需求轴通过，规范轴失败。**

分别报告可以避免一个轴的结果掩盖另一个轴的问题。
