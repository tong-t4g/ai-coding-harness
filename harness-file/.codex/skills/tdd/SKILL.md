# 测试驱动开发

TDD 就是红 → 绿循环。本 skill 是让该循环产出值得长期保留的测试的参考：什么是好测试、测试应该放在哪里、常见反模式，以及循环规则。每一轮都适用全部章节；应在循环前和循环中查阅，而不是事后补看。

探索代码库时，如果存在 `CONTEXT.md`，先阅读它，使测试名称和接口词汇符合项目领域语言；同时遵守正在修改区域的 ADR。

## 什么是好测试

测试通过公开接口验证行为，而不是实现细节。代码可以彻底变化，测试不应因此失效。好测试应像规格一样可读——“用户可以使用有效购物车结算”准确描述了存在的能力，并且不关心内部结构，所以能经受重构。

示例见 [tests.md](tests.md)，Mock 指南见 [mocking.md](mocking.md)。

## 测试接缝：测试应该放在哪里

**测试接缝（seam）**是测试所处的公开边界：在不深入内部实现的情况下观察行为的接口。测试应位于接缝上，绝不能针对内部实现。

**只在预先约定的接缝上测试。** 编写测试前，先写明待测接缝并与用户确认。未经确认的接缝不得编写测试。无法测试一切；提前约定接缝，才能让测试投入覆盖关键路径和复杂逻辑，而不是平均分散到每个边界情况。

询问：“公开接口是什么？我们应该测试哪些接缝？”

## 反模式

- **与实现耦合**：Mock 内部协作者、测试私有方法，或通过旁路验证（例如查询数据库而不是使用接口）。典型表现是：重构后行为没变，测试却失败。
- **同义反复**：断言按与代码相同的方式重新计算期望值（`expect(add(a, b)).toBe(a + b)`、用同样方式手工推导的快照、断言常量等于自身），测试因此必然通过，永远无法与代码产生分歧。期望值必须来自独立真值来源，例如已知正确的字面量、推导示例或规格。
- **水平切片**：先编写全部测试，再编写全部实现。批量测试验证的是_想象中的_行为，测试对象是结构而不是用户可见行为，因而对真实变化不敏感；并且在理解实现前就锁定了测试结构。应改用**垂直切片**：一个测试 → 一个实现 → 重复，每一轮测试都是响应上一轮认知的**示踪弹**。

## 循环规则

- **先红后绿。** 先编写失败测试，再只写足以通过它的代码。不要预判未来测试，也不要添加推测性功能。
- **一次一个切片。** 每轮只处理一个接缝、一个测试和一个最小实现。
- **重构不属于循环。** 重构应放在审查阶段（见 `code-review` skill），而不是红 → 绿实现循环中。
