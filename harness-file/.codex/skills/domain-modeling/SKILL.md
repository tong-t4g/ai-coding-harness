# 领域建模

设计过程中主动构建并打磨项目的领域模型。这是一套*主动建模*纪律：质疑术语、设计边界场景，并在术语和决策明确的瞬间立即写入术语表和决策记录。（仅仅为了了解词汇而*阅读* `CONTEXT.md` 不属于本 skill；任何 skill 都可以做到这一点。本 skill 用于修改领域模型，而不只是消费它。）

## 文件结构

大多数仓库只有一个上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `CONTEXT-MAP.md`，说明仓库有多个上下文。该映射文件会指出每个上下文的位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← system-wide decisions
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← context-specific decisions
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

按需创建文件，只在确实有内容需要写入时创建。如果不存在 `CONTEXT.md`，在第一个术语确定时创建；如果不存在 `docs/adr/`，在首次需要 ADR 时创建。

## 会话期间

### 对照术语表提出质疑

当用户使用的术语与 `CONTEXT.md` 中已有的统一语言冲突时，立即指出：“术语表将 ‘cancellation’ 定义为 X，但你似乎指的是 Y；究竟是哪一个？”

### 精确化模糊语言

当用户使用含糊或过载的术语时，提出精确的规范术语：“你说的是 ‘account’——你指的是 Customer 还是 User？它们是两个不同的概念。”

### 讨论具体场景

讨论领域关系时，用具体场景进行压力测试。设计能够探查边界情况的场景，促使用户准确说明概念之间的边界。

### 与代码交叉核对

当用户描述某项行为时，检查代码是否一致。如果发现矛盾，明确指出：“你的代码会取消整个 Order，但你刚才说可以部分取消；哪一个才是正确的？”

### 就地更新 CONTEXT.md

术语确定后立即更新 `CONTEXT.md`，不要积累到最后批量处理；在决策发生时就记录。使用 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) 中的格式。

`CONTEXT.md` 必须完全不包含实现细节。不要把它当作规格、草稿或实现决策仓库；它只能是术语表。

### 谨慎提出 ADR

只有同时满足以下三个条件时，才建议创建 ADR：

1. **难以逆转**：之后改变决定的成本很高
2. **缺少上下文就令人意外**：未来读者会疑惑“为什么要这样做？”
3. **源于真实取舍**：存在实际替代方案，并基于具体理由选择了其中一个

缺少任一条件就跳过 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。
