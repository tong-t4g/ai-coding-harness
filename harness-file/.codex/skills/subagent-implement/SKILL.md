# 子智能体驱动开发

用一条可恢复的闭环执行计划：**并行实现 -> 任务审查 -> 修复复审 -> 串行集成 -> 整分支审查**。

控制器负责拆分上下文、创建 worktree、分派、裁定、集成和记录；实现代码始终由对应任务的实现者在专属 worktree 中修改并进行独立审查。

## 适用条件

仅在以下条件全部成立时使用：

1. 已有用户批准的实现计划，且任务和验收条件明确。
2. 每项任务可从同一个分支起点独立实现、提交、编译和验证。
3. 任务要在当前会话内连续执行。

计划中任何任务依赖另一任务的未集成产出，或多个任务会修改同一文件时，不得使用本 skill；改用当前会话按任务顺序执行。平台并发槽不足时可以分批启动实现者，但每个任务仍使用独立 worktree。

## 1. 建立执行上下文

1. 读取适用的 `AGENTS.md`、计划和计划引用的项目规则。
2. 确认当前分支和主工作树干净。主分支只有在用户明确同意后才能作为实现分支；计划、状态文件和已有改动必须先提交。
3. 记录分支起点 `MERGE_BASE`；它是最终审查范围的起点。
4. 运行 `scripts/sdd-workspace PLAN_FILE`，取得本计划唯一的工作区路径。
5. 读取 `<工作区>/progress.md`。若文件不存在，第一行写入：
   `# SDD 进度账本 - 计划: <计划文件绝对路径>`。
6. 从账本恢复已审查、已集成任务和未结束的修复轮次，再为剩余任务建立待办。
7. 一次性检查任务依赖、修改文件重叠、全局约束冲突，以及计划要求与审查规则冲突。任务必须能从同一个 `MERGE_BASE` 独立完成；不能确认时停止并交给用户裁定。
8. 对全部未集成任务运行 `scripts/task-worktree prepare PLAN_FILE MERGE_BASE N...`。脚本标准输出的唯一一行是 worktree 清单路径；从清单读取每个任务的专属工作目录。

脚本是 Bash 脚本。在 PowerShell 中没有 `bash` 命令时，使用 Git Bash 的可执行文件调用；不得手工仿写脚本的确定性转换逻辑。

完成条件：计划路径、当前分支、`MERGE_BASE`、SDD 工作区、worktree 清单、全局约束、任务列表和恢复位置均已确定，所有任务相互独立且已获得专属 worktree。

## 2. 选择子智能体

每次分派都显式选择平台支持的、能可靠完成该角色的最低能力档位：

- 规格完整、只涉及 1-2 个文件的机械任务：快速档。
- 跨文件集成、调试或需要模式判断：标准档。
- 架构决策、高风险改动和最终整分支审查：最高能力档。

平台不提供档位选择时使用默认模型，不得因此阻塞流程。尽量在同一轮中并行分派全部实现任务；超过平台并发上限时，按可用槽位分批启动。每个 worktree 同时只能有一个写入者，但不同任务 worktree 可以并行写入和审查。

worktree 统一由 `scripts/task-worktree` 管理。不得再启用 Claude Code 的 `isolation: worktree`、Codex 会话级 worktree 或其它平台文件隔离，否则会产生嵌套 worktree。只启用独立子智能体上下文；平台不支持上下文隔离时使用默认行为。

## 3. 并行实现与任务审查

### 3.1 准备并分派

1. 将本任务的 `BASE` 固定为 `MERGE_BASE`，从 worktree 清单读取 `WORKDIR`。
2. 运行 `scripts/task-brief PLAN_FILE N`。脚本标准输出的唯一一行是任务简报路径。
3. 将报告路径设为同目录的 `task-N-report.md`。
4. 使用 [implementer-prompt.md](implementer-prompt.md) 分派一个全新的实现者，传入 `WORKDIR`。仅隔离父会话上下文，不启用平台 worktree isolation。
5. 只传递任务简报、适用的全局约束、任务所需的既有接口与裁定、工作目录和报告路径。精确需求只保留在任务简报中。
6. 记录实现者身份；后续修复优先恢复这个实现者。

全部任务的步骤 1-6 准备完成后再统一分派。完成条件：每个实现者拥有完成自身任务所需且仅限自身任务的上下文，`BASE`、`WORKDIR`、简报和报告路径均已记录。

### 3.2 处理实现者状态

实现者必须返回以下状态之一：

| 状态 | 控制器动作 |
|---|---|
| `DONE` | 核对报告和测试证据，进入任务审查。 |
| `DONE_WITH_CONCERNS` | 正确性或范围疑虑先解决；观察性疑虑写入账本后进入审查。 |
| `NEEDS_CONTEXT` | 补充明确缺失的事实，恢复原实现者。 |
| `BLOCKED` | 改变条件后再分派：补上下文、拆任务或提升模型；计划缺陷交给用户裁定。 |

同一失败条件下不得原样重试。实现者有问题时先回答，不能用催促代替缺失信息。

完成条件：状态已被显式处理；进入审查时，报告包含提交、改动摘要、测试命令、测试结果和遗留疑虑。

### 3.3 任务审查

1. 令 `HEAD=$(git -C WORKDIR rev-parse HEAD)`，运行 `scripts/review-package PLAN_FILE BASE HEAD <工作区>/task-N-review.diff`。
2. 使用 [task-reviewer-prompt.md](task-reviewer-prompt.md) 分派只读审查者，输入 `WORKDIR`、简报、报告、审查包和约束当前任务的全局规则。
3. 审查报告必须同时给出“规格结论”和“质量结论”。
4. 对“无法从 diff 核实”的每一项，由控制器查阅计划和跨任务上下文；真实缺口按规格失败处理。

完成条件：每项规格要求都有结论，每项发现都有严重级别和证据，且两个审查结论均存在。

### 3.4 修复循环

规格失败、严重问题或重要问题进入修复循环。次要问题写入账本：
`任务 N：次要问题（待最终审查）：<一句话>`。

发现与计划原文冲突时，先把发现和原文交给用户裁定。不得分派违反计划的修复，也不得用计划原文压掉真实缺陷。

每轮修复执行以下步骤，最多三轮：

1. 在任务 worktree 中记录 `FIX_BASE`，把全部未关闭发现原文交给原实现者；原实现者不可用或已 `BLOCKED` 时，分派新的实现者并附 `WORKDIR`、简报、报告和既往尝试。
2. 实现者修复、提交，重跑覆盖改动的测试，并把改动、测试文件、命令和输出追加到原报告。
3. 核对修复报告证据齐全。
4. 令 `HEAD=$(git -C WORKDIR rev-parse HEAD)`，运行 `scripts/review-package PLAN_FILE FIX_BASE HEAD <工作区>/task-N-fix-R-review.diff`，使用 [re-review-prompt.md](re-review-prompt.md) 在同一 `WORKDIR` 做范围复审。
5. 未解决发现和修复引入的严重、重要问题进入下一轮；次要问题写入账本。
6. 追加账本：`任务 N：修复轮次 R/3（已解决 X，未解决 Y，提交 a..b）`。

第三轮后仍有规格缺口、严重问题或重要问题时，追加
`任务 N：BLOCKED - <未解决问题>`，向用户报告修复历史并停止。不能把它记为完成。

完成条件：规格通过、质量通过、所有严重和重要问题已关闭，且所有次要问题已进入账本。

### 3.5 记录任务审查通过

在同一检查点更新待办和账本：
`任务 N：worktree 审查通过（提交 base..head，规格通过，质量通过，待集成）`。

此时不得更新计划 checkbox 或 `.codeforge-state.yaml`。其它任务无需等待即可继续；上下文压缩后，以账本、worktree 清单和对应 worktree 的 `git log` 为准，不重新分派已审查任务。

## 4. 串行集成

全部任务的 worktree 审查通过且没有 `BLOCKED` 后，按任务编号依次集成：

1. 确认主工作树干净，运行 `scripts/task-worktree integrate PLAN_FILE N`。脚本使用 `cherry-pick --no-commit` 暂存任务 worktree 的全部提交；冲突时保留现场并显式 `BLOCKED`，不能自动解决。
2. 运行计划要求的编译检查。失败说明任务独立性判断或跨任务组合有误；保留当前集成现场并显式 `BLOCKED`。
3. 将计划文件中该任务的所有 checkbox 更新为已完成，并更新共享状态文件的 checkpoint。
4. 把任务代码、计划和状态文件提交为一个最终任务 commit。
5. 运行 `scripts/task-worktree record PLAN_FILE N HEAD`，记录该任务的集成提交，并追加账本：`任务 N：已集成（提交 <sha>）`。
6. 主工作树恢复干净后才可集成下一个任务。

断点恢复时，若主工作树因 `integrate` 留有暂存改动，不得再次运行 `integrate`；先核对任务差异并完成步骤 2-5。若最终任务 commit 已存在但清单尚未记录，直接补跑 `record`。

完成条件：所有任务均按编号集成；每项任务在最终分支上只有一个包含代码、计划和状态的 commit；主工作树干净。

## 5. 最终整分支审查

1. 确认所有任务均有完成记录且没有 `BLOCKED`。
2. 运行 `scripts/review-package PLAN_FILE MERGE_BASE HEAD`。
3. 使用最高能力档和 [final-reviewer-prompt.md](final-reviewer-prompt.md) 分派只读审查者，输入完整计划、审查包、进度账本和项目规则。
4. 最终发现按同一严重级别处理。每轮把全部未关闭问题交给一个修复者，修复后做范围复审，最多三轮。
5. 三轮后仍有规格缺口、严重问题或重要问题时，显式报告 `BLOCKED`。
6. 审查和计划验证全部通过后，运行 `scripts/task-worktree cleanup PLAN_FILE` 清理任务 worktree。清理失败必须报告，不能把流程记为完成。

完成条件：最终规格和质量结论均通过；所有严重、重要问题已关闭；每个次要问题都有“修复”或“接受风险”的明确结论；计划要求的验证均有命令和结果证据；所有任务 worktree 已清理。

## 硬性边界

- 每个任务 worktree 同时只能有一个实现者写入；实现者不得写入其它任务 worktree 或主工作树。
- 任务实现与审查可以并行，主工作树集成必须按任务编号串行。
- 实现者不得修改共享计划、状态文件或进度账本；这些文件只由控制器在集成时更新。
- 不得使用平台 worktree isolation；任务 worktree 只能由 `scripts/task-worktree` 创建和清理。
- 审查范围始终使用记录的 `BASE..HEAD`；`HEAD~1` 不能替代任务起点。
- 实现者自审不能替代独立任务审查。
- 任何发现都必须被修复、记录为次要问题，或以 `BLOCKED` 暴露；不存在静默丢弃路径。
