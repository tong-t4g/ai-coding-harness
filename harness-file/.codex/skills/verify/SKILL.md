# 完成验证

坚持一个原则：**证据先于结论，结论不得超出证据覆盖范围。**

验证证据只对产生它的工作状态有效。代码、配置、依赖、生成物或运行环境发生相关变化后，重新运行受影响的验证。

## 验证门禁

### 1. 明确待证明的结论

重新读取用户请求、规格、计划或验收标准，并检查实际变更。把准备作出的完成声明拆成可独立判断的结论，例如“目标测试通过”“项目可构建”“原缺陷不再出现”“所有验收标准已满足”。避免把局部验证表述成全局结论。

**完成条件：** 每项准备声明的结论均已列出，且范围明确。

### 2. 为每项结论选择证据

优先从仓库文档、构建配置、CI 配置和现有脚本中确定权威验证命令。根据改动范围补充需求核对、静态检查、构建、测试或人工复现；没有单条命令可以证明“需求全部满足”。

| 结论 | 至少需要的证据 |
| --- | --- |
| 测试通过 | 对应范围的测试命令完成，输出中无失败；跳过项已核实 |
| 构建成功 | 对应范围的构建命令以成功状态完成，并生成预期产物（如适用） |
| 静态检查通过 | 对应检查命令完成，目标范围内无错误 |
| 缺陷已修复 | 在当前实现上复现原始场景，原症状消失且预期行为出现 |
| 回归测试有效 | 已观察该测试在缺陷存在时失败、修复后通过；否则只声明当前测试通过 |
| 需求已完成 | 每条验收标准均映射到实现、测试、检查结果或人工验证证据 |
| 子智能体任务完成 | 独立检查实际变更，再运行与声明匹配的验证；报告本身不算证据 |

全量结论需要全量证据；局部证据只能支持带有明确范围的局部结论。无法安全运行会修改外部状态的验证时，使用已获授权的替代证据，或将该项标记为未验证。

**完成条件：** 每项结论均已映射到足以证实或证伪它的证据，且验证范围不小于声明范围。

### 3. 在当前工作状态执行验证

运行完整命令并等待结束。保留命令、退出码和关键输出；同时检查失败数、跳过数、警告、实际执行范围及预期产物。退出码为 `0` 是证据的一部分，不单独等于通过。

以下结果均不是通过证据：

- 相关改动之前的历史结果；
- 超时、中断、输出被截断或状态不明的命令；
- 用静态检查代替构建，或用局部测试推断全量测试；
- “理论上可行”“应该通过”等推断；
- 未经独立核实的子智能体报告。

**完成条件：** 所有计划验证均在当前相关工作状态上执行完毕，结果完整且可判读。

### 4. 按证据判定状态

逐项使用以下状态，不把失败或缺证据包装成完成：

- **通过**：基于当前工作状态的完整证据支持结论，且没有影响该结论的未解释失败或跳过项。
- **失败**：验证结果与结论冲突。
- **未验证**：证据缺失、过期、不完整、范围不足或结果含糊。
- **受阻**：所需验证因权限、环境、依赖或外部系统不可用而无法执行。

警告和跳过项需要判断是否影响结论。只有确认其不在声明范围内并说明理由时，才不阻止通过。检查失败后，报告实际状态；修复相关问题后，从受影响的验证开始重跑。

**完成条件：** 每项结论均有唯一状态，所有失败、跳过和限制均已记账。

### 5. 报告结论与证据

使用简洁、可复核的格式：

```markdown
验证状态：通过 | 失败 | 未验证 | 受阻

- 结论：<被验证的具体结论和范围>
- 证据：`<命令或检查>`；退出码 <n>；<关键结果>
- 异常：<失败、警告、跳过项或“无”>
- 限制：<未覆盖范围或“无”>
```

有多项结论时逐项报告。只有全部必需结论均为“通过”时，才能声明对应工作完成；否则准确说明已验证部分、剩余问题和下一步。

**完成条件：** 最终措辞与证据和状态完全一致，读者可以据此复核，不依赖信心或推测。
